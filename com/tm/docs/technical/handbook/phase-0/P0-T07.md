## Build chéo bằng Bazel platform
- **Chủ đề**: `bazel/platform`, `go/cross-compile`
- **Bối cảnh**: dev trên macOS arm64, container chạy Linux (arm64 trên Mac, amd64 trên server).
- **Cách làm & lý do**: `platform(name = "linux_arm64" | "linux_amd64", constraint_values = ["@platforms//os:linux", "@platforms//cpu:..."])` trong `BUILD.bazel` gốc; `.bazelrc` đặt tên tắt `build:linux-arm64 --platforms=//:linux_arm64`. `--platforms` = build **cho** máy nào; không đặt → build cho máy đang chạy. Go thuần + CGO tắt (P0-T04) nên rules_go chỉ đổi `GOOS/GOARCH`, không cần C compiler Linux → binary `statically linked`, chạy được trên image không có libc.
- **Bẫy / lưu ý**: `bazel-bin/.../server` bị ghi đè theo config vừa build — kiểm tra bằng `file` ngay sau mỗi lần build.
- **Code**: [BUILD.bazel#L15-L29 — linux_arm64, linux_amd64](../../../../server/BUILD.bazel#L15-L29), [.bazelrc](../../../../server/.bazelrc)

## Image OCI không cần Dockerfile: rules_oci, distroless static, pin digest
- **Chủ đề**: `docker/oci`, `bazel/rules_oci`, `security/container`
- **Bối cảnh**: đóng core thành image nhỏ, an toàn, build tái lập, không phụ thuộc Docker daemon khi build.
- **Cách làm & lý do**: image OCI = manifest → **config JSON** (entrypoint, user, env, port) + danh sách **layer** (mỗi layer là một tar). rules_oci tự ghép: `copy_file` (rules_go để binary ở `server_/server`, copy ra `bin/server` cho entrypoint ổn định) → `tar` (layer; giữ đường dẫn package → `/services/core/cmd/server/bin/server`) → `oci_image` (base + layer + config) → `oci_load` (chỉ bước này cần Docker: nạp vào Docker local với tag). Base `gcr.io/distroless/static-debian12:nonroot`: không shell, không libc, không package manager → 17 MB, ít CVE, vào được container cũng không có `sh`; Go tĩnh không cần libc nên không dùng `distroless/base` như thor. `oci.pull` pin **digest** của image index multi-arch (tag có thể bị trỏ sang image khác, digest là hash nội dung); tạo alias `@distroless_static` tự chọn manifest amd64/arm64 theo `--platforms`. `user = "65532:65532"` ghi rõ trong config.
- **Bẫy / lưu ý**: trên macOS cần `--strategy=CopyFile=local` và `--strategy=CopyToDirectory=local` (không chạy được trong darwin-sandbox) và `--repo_env=DOCKER_CONFIG=/dev/null` (lấy từ thor). Base không có bản darwin → mọi target image gắn `target_compatible_with = ["@platforms//os:linux"]`: `bazel build //...` không `--config` bỏ qua chúng, gọi thẳng thì báo "incompatible". Build tái lập: digest image giống hệt sau `bazel clean` (TC07) — Bazel cố định mtime/owner trong tar. `docker stop` chỉ 0.26s vì binary là PID 1 nhận SIGTERM trực tiếp; entrypoint dạng `sh -c` sẽ nuốt signal → chờ 10s rồi SIGKILL.
- **Code**: [MODULE.bazel#L37-L46 — oci.pull distroless_static](../../../../server/MODULE.bazel#L37-L46)
- **Tham khảo**: [rules_oci](https://github.com/bazel-contrib/rules_oci), [distroless](https://github.com/GoogleContainerTools/distroless)

## Macro com_tm_go_image theo cấu trúc thor
- **Chủ đề**: `bazel/starlark`, `bazel/macro`
- **Bối cảnh**: mọi binary Go cần cùng một bộ target image; không muốn copy khối BUILD cho từng service.
- **Cách làm & lý do**: macro = hàm Starlark gọi nhiều rule lúc Bazel đọc BUILD, sau đó biến mất (`bazel query` chỉ thấy target thật). Tách như thor: `_container_targets` (phần chung mọi ngôn ngữ: `_tar` → `_image` → `_docker` → `_push` chỉ khi có `repository`) và `com_tm_go_image` (phần riêng Go: `go_binary(pure, static)` + `copy_file` + gọi helper). Khác thor: attr `image_name` (tag `com.tm.go.core-server:v1.0.0` trong khi target vẫn tên `server`, `image_name or name` là cách đặt mặc định trong Starlark); entrypoint tính bằng `native.package_name()` thay vì bắt truyền `package_name` (target do gazelle sinh không có attr đó); user nonroot + Linux-only đặt trong helper. Chọn **legacy macro** thay vì symbolic macro của Bazel 8 vì gazelle cần đọc/sửa attr (`embed`) như một rule thường. Tên bắt đầu `_` là private trong `.bzl`. `tools/BUILD.bazel`, `tools/rules/BUILD.bazel` (rỗng) để thư mục thành package, `load("//tools/rules:...")` mới tìm được.
- **Bẫy / lưu ý**: không có unit test tự động cho image ở task này — `container_structure_test` driver `tar` cần thêm dependency + target tarball, và binary kiểm tra chọn theo platform đích (dễ lấy nhầm bản Linux khi test từ macOS với `--config=linux-*`); kiểm bằng test case manual, integration ở P0-T08.
- **Code**: [tools/rules/com_tm_container.bzl#L33-L95 — _container_targets](../../../../server/tools/rules/com_tm_container.bzl#L33-L95), [com_tm_container.bzl#L101-L160 — com_tm_go_image](../../../../server/tools/rules/com_tm_container.bzl#L101-L160)

## Gazelle map_kind: mọi binary tự có image
- **Chủ đề**: `bazel/gazelle`
- **Bối cảnh**: gazelle mặc định sinh `go_binary` trơn; muốn service mới có image mà không ai phải nhớ.
- **Cách làm & lý do**: `# gazelle:map_kind go_binary com_tm_go_image //tools/rules:com_tm_container.bzl` — gazelle vẫn phân tích như `go_binary` nhưng ghi ra kind `com_tm_go_image` + tự thêm/bỏ `load`; khi đọc lại coi nó là `go_binary` nên vẫn cập nhật `embed`. Thử thật: đổi target về `go_binary` → gazelle viết lại đúng như cũ; tạo `package main` mới → BUILD sinh thẳng `com_tm_go_image`, có ngay `_image`, `_docker`. Gazelle chỉ ghi đè attr nó hiểu (`embed`, `srcs`, `deps`...), giữ attr lạ (`image_name`, `exposed_ports`).
- **Bẫy / lưu ý**: trước khi có `map_kind`, gazelle **không** sinh `go_binary` trùng tên khi đã có rule `server` kind lạ — nó bỏ qua (khác dự đoán ban đầu); nhưng khi đó nó cũng không quản lý attr của target đó nữa.
- **Code**: [BUILD.bazel#L8-L10 — map_kind](../../../../server/BUILD.bazel#L8-L10), [services/core/cmd/server/BUILD.bazel — com_tm_go_image server](../../../../server/services/core/cmd/server/BUILD.bazel)
